# ТЗ: ML

## Роль

Зона ответственности: три модели качества, детектор аномалий, Парето-оптимизатор. Всё, что связано с прогнозом и подбором управляющих воздействий. Data layer, HTTP-API, оркестратор агентов, интеграция с GigaChat и фронтенд лежат вне этой зоны.

## Контекст

Общая задача проекта: МАС-советник для оператора НПЗ по цепочке АВТ, гидроочистка, блендинг. От ML нужен «оракул», к которому обращаются агенты: прогноз качества на срез процесса, оценка риска нарушения спеки, предложение допустимых вариантов изменения режима. При недостатке данных модели обязаны возвращать явный флаг низкой уверенности.

## Состав работ

Реализуются пять компонентов:

1. Модель качества АВТ. Прогноз показателей дизельной фракции 240-350 на выходе АВТ: T50, T90, D15, ПТФ.
2. Модель качества гидроочистки. Прогноз содержания серы (главный таргет всей системы, лимит 10 мг/кг), а также T50, T90, D15 гидроочищенного дизеля.
3. Модель блендинга. Физическая, не ML. Считает свойства смеси по свойствам компонентов и их массовым долям.
4. Детектор аномалий. Флаги на срез процесса: аномальные значения, застывшие сигналы, выход режима за пределы исторического «облака».
5. Парето-оптимизатор. Для среза и набора ограничений возвращает 10 допустимых вариантов управляющих воздействий, отранжированных как Парето-фронт по нескольким метрикам.

## Вне зоны ответственности

- HTTP-роуты, FastAPI, интеграция с фронтом.
- Оркестратор агентов и логика ответа (`recommend` / `silent` / `refuse`).
- Промпты для GigaChat, MCP-сервер, форматирование текста рекомендации.
- Загрузка сырых CSV/XLSX и склейка по времени. Всё это делает data layer, на выход подаётся готовый `DataFrame`.
- Отрисовка SHAP-графиков на фронте. ML отдаёт числовые данные, визуализация лежит на фронтенде.
- Docker, инфраструктура, деплой.
- Проектирование архитектуры мультиагентной системы.

## Данные

Исходники лежат в папке хакатона (в git не коммитится, локально принято класть в `hackathon/`). Data layer читает их, конвертирует в parquet-кеш в `data/`, откуда работают все ML-скрипты.

Источники (пути относительно папки хакатона):
- `data/avt_tags.csv` - телеметрия АВТ, 74 датчика, 10-минутные ряды, 2023-01-01 до 2026-08-07.
- `data/242000_tags.csv` - телеметрия гидроочистки, 28 датчиков, тот же формат.
- `Выгрузка ПАК ...xlsx` - поточные анализаторы: сера каждые 10 минут, плотность D15.
- `ЛИМСы ...xlsx` - лабораторные анализы, редкие и асинхронные.
- `Теги_хакатон.xlsx` - справочник: листы КИП, ЛА, ПАК, ВАК. На листе ВАК есть готовые формулы виртуальных анализаторов, они используются как база модели.
- `АВТ_схемы.pdf` - схемы установок.
- `ТЗ_нефтекод.docx` - исходное ТЗ хакатона.

Подробный разбор форматов и подводных камней - в `docs/tz/data_reference.md`.

Приоритет источников качества: ЛИМС выше ПАК, ПАК выше расчётных формул ВАК. При расхождении контрольным считается лабораторный результат.

Правила:
- Синхронизация источников только по метке времени `date`, не по номеру строки.
- Возраст последнего лабораторного значения (в часах) обязательно попадает в фичи модели.
- Для прогноза на момент T нельзя использовать данные с меткой позднее T. Утечка будущего проверяется тестом.

## Требуемые классы и API

Всё ML-ядро оборачивается в фиксированные классы. Их сигнатуры согласуются с AI-агентщиком в первый день работы и после этого не меняются.

### Общие типы (`backend/ml/types.py`)

```python
@dataclass
class Interval:
    mean: float
    low: float          # квантиль 0.1
    high: float         # квантиль 0.9
    unit: str

@dataclass
class QualityPrediction:
    predictions: dict[str, Interval]      # например {"sulfur_ppm": Interval(...), "T50": Interval(...)}
    spec_risk: dict[str, float]           # вероятность выхода за спеку, например {"sulfur_over_10": 0.27}
    confidence: Literal["high", "medium", "low"]
    warnings: list[str]                   # человекочитаемые предупреждения

@dataclass
class Explanation:
    top_features: list[tuple[str, float]] # (имя фичи, значение SHAP), отсортировано по |value|
    base_value: float                     # базовое предсказание модели

@dataclass
class AnomalyReport:
    is_anomaly: bool
    anomaly_score: float                  # 0..1
    flagged_tags: list[str]
    is_out_of_envelope: bool
    stale_tags: list[str]                 # теги, не менявшиеся больше порога

@dataclass
class Component:
    name: str
    properties: dict[str, float]          # {"sulfur_ppm": 8.2, "D15": 831.5, "T50": 285, ...}
    mass_flow: float                      # т/ч

@dataclass
class BlendedProduct:
    properties: dict[str, float]
    total_mass: float

@dataclass
class OptimizationConstraints:
    hard: dict[str, tuple[float, float]]           # жёсткие спеки, например {"sulfur_ppm": (0, 10)}
    controllable_ranges: dict[str, tuple[float, float]]  # диапазоны управляемых тегов
    max_deviation_pct: float                       # максимальное отклонение от текущего значения

@dataclass
class Variant:
    action: dict[str, float]              # {"T55": 348.0, "F30": 44.5, ...}
    expected: QualityPrediction
    metrics: dict[str, float]             # {"sulfur": 6.4, "yield": 0.85, "energy": 1.11, "severity": 0.3}
    feasible: bool
    infeasible_reason: str | None
```

### Модели качества

Файл `backend/ml/models/quality_avt.py`:

```python
class QualityAVTModel:
    @classmethod
    def load(cls, path: str) -> "QualityAVTModel": ...
    def predict(self, state: pd.DataFrame) -> QualityPrediction: ...
    def predict_after_action(self, state: pd.DataFrame, action: dict[str, float]) -> QualityPrediction: ...
    def explain(self, state: pd.DataFrame) -> Explanation: ...
```

Файл `backend/ml/models/quality_hydro.py`: идентичный интерфейс, класс `QualityHydroModel`.

Требования к обеим моделям:
- Базовый прогноз - формула ВАК из справочника. Поверх обучается LightGBM на резидуалах.
- Uncertainty реализуется через квантильную регрессию (три модели: q=0.1, q=0.5, q=0.9).
- Метод `predict` принимает срез процесса на момент T (одна строка `DataFrame` с фичами), возвращает `QualityPrediction`.
- Метод `predict_after_action` принимает срез плюс словарь изменений тегов, возвращает прогноз после применения действия.
- Метод `explain` возвращает топ-10 признаков по SHAP для последнего вызова.
- Каждый вызов пишет в лог входные фичи и результат (для трейсинга).

Специфично для `QualityHydroModel`: recall превышений лимита 10 мг/кг на тесте не ниже 90%. Пропуск нарушения спеки недопустим.

### Модель блендинга

Файл `backend/ml/models/blending.py`. Физика, не ML.

```python
class BlendingModel:
    def blend(self, components: list[Component], fractions: list[float]) -> BlendedProduct: ...
```

Правила смешения:
- Линейные (сера, D15, T50, T90): взвешенное среднее по массовым долям.
- Нелинейные (вязкость - Refutas index, ПТФ - blending index): стандартные формулы.
- Проверка баланса: `sum(fractions) == 1.0` с допуском 1e-6, иначе `ValueError`.
- Unit-тесты: смешение с самим собой возвращает те же свойства; линейность на 50/50 смеси.

### Детектор аномалий

Файл `backend/ml/models/anomaly.py`.

```python
class AnomalyDetector:
    @classmethod
    def load(cls, path: str) -> "AnomalyDetector": ...
    def score(self, state: pd.DataFrame) -> AnomalyReport: ...
```

Внутренняя реализация: Isolation Forest на нормализованных фичах плюс rolling z-score по каждому тегу. Обучение unsupervised на «нормальных» периодах (без известных инцидентов).

### Оптимизатор

Файл `backend/ml/optimizer/pareto.py`.

```python
class ParetoOptimizer:
    def __init__(self, quality_avt: QualityAVTModel, quality_hydro: QualityHydroModel, blending: BlendingModel): ...
    def find_pareto(
        self,
        state: pd.DataFrame,
        constraints: OptimizationConstraints,
        n_variants: int = 10,
    ) -> list[Variant]: ...
```

Требования:
- Алгоритм: Bayesian optimization через Optuna. При наличии времени - NSGA-II через pymoo.
- Метрики Парето: сера (min), выход товарного ДТ (max), энергозатраты как прокси (min), тяжесть режима (min).
- Все варианты проверяются на жёсткие ограничения из `constraints.hard`. Нарушающие отбрасываются с указанием причины в `Variant.infeasible_reason`.
- Фильтр по плотности: варианты, попадающие в области с малой плотностью исторических данных (out-of-envelope), помечаются `feasible=False` с причиной `"low_historical_density"`.
- Скорость: возврат 10 вариантов быстрее 5 секунд для одного среза.

## Feature Engineering

Общие подходы, применяемые ко всем моделям:
- Скользящие статистики (mean, std, slope) за окна 30, 60, 120 минут.
- Лаги 10, 30, 60 минут для ключевых тегов.
- Возраст последнего значения ЛИМС по каждой точке отбора.
- Кумулятивные признаки (наработка катализатора и т.п.) как прокси для деградации.
- Для модели гидроочистки: сдвиг признаков АВТ на эмпирическую задержку (кросс-корреляция).

Все фичи и таргеты описываются в реестре `backend/data_layer/feature_registry.yaml`. Формат каждой записи: тег, источник, единица, роль (`feature` или `target`), управляемость, диапазон. Реестр - единый source of truth. Оптимизатор и агенты берут границы управляемых параметров именно оттуда.

## Валидация

Единственный допустимый режим - walk-forward, без перемешивания строк.

Разбивка по времени:
- Обучение: 2023-01-01 до 2024-12-31.
- Валидация (тюнинг): 2025-01-01 до 2025-06-30.
- Тест (финальный отчёт): 2025-07-01 до 2026-08-07.

Метрики, попадающие в отчёт:
- MAE и RMSE по каждому таргету.
- Coverage 90%-интервала. Целевой диапазон: 85-95%.
- Для серы дополнительно: precision, recall, F1 по бинарной метке «превышение 10 мг/кг».
- Сравнение с baseline: чистая формула ВАК без ML сверху. Если ML не обгоняет формулу по MAE, ML-часть исключается.

## Обучение

Все обученные модели сохраняются в `backend/ml/artifacts/*.pkl`. Артефакты не коммитятся в git.

Обёртка для обучения всей системы: `backend/ml/training/train_all.py`. Один запуск через `make train` должен:
1. Прочитать parquet-кеш из `data/`.
2. Собрать фичи.
3. Обучить `QualityAVTModel`, `QualityHydroModel`, `AnomalyDetector`.
4. Сохранить артефакты.
5. Прогнать walk-forward валидацию.
6. Записать `backend/ml/artifacts/metrics_report.json`.

Промежуточные скрипты (обучение отдельных моделей) лежат в том же каталоге.

## Взаимодействие

На вход подаётся:
- `pd.DataFrame` со склеенной телеметрией, ПАК и ЛИМС от data layer.
- Симулятор реалтайма (функция `get_state(timestamp)`), возвращающая срез без утечки будущего.
- Метаданные тегов в формате `dict` (unit, controllable, range, description).

Наружу отдаётся:
- Пять классов с фиксированным API (см. раздел «Требуемые классы и API»).
- Документ `docs/api_ml.md` с примерами вызовов и форматами ответов.
- Feature registry.

Точки синхронизации:
- Первый день: API классов согласован с AI-агентщиком, зафиксирован в `docs/api_ml.md`, дальше не меняется.
- Изменение API после фиксации возможно только через явное согласование.
- Перед демо: совместный прогон всех сценариев end-to-end с оркестратором.

## Порядок работы

Приоритет: сначала baseline всех пяти компонентов, затем улучшения. Углубление в одну модель до готовности baseline остальных запрещено.

Последовательность:
1. Baseline `QualityAVTModel` (LightGBM + ВАК-фичи).
2. Baseline `QualityHydroModel` с фокусом на серу.
3. Реализация `BlendingModel` (физика).
4. `AnomalyDetector` (Isolation Forest).
5. `ParetoOptimizer` (Optuna, простая реализация).

После этого - вторая итерация по каждому компоненту:
- Feature engineering (лаги, скользящие, задержки между стадиями).
- Uncertainty через квантильную регрессию.
- SHAP-объяснения.
- Walk-forward отчёт.
- Полировка оптимизатора: Парето, фильтр по плотности исторических данных.

## Критерии приёмки

Работа принимается, если выполнены все пункты:
1. Все пять классов реализованы и покрыты минимальными smoke-тестами.
2. Обученные модели сохранены в `backend/ml/artifacts/`.
3. Модели качества имеют coverage 90%-интервала в диапазоне 85-95% на тесте.
4. Модель серы имеет recall превышений 10 мг/кг не ниже 90% на тесте.
5. Все модели качества обгоняют baseline (ВАК-формулу) по MAE.
6. `predict` одного среза выполняется быстрее 100 мс.
7. `find_pareto` возвращает 10 вариантов быстрее 5 секунд.
8. Feature registry заполнен для всех используемых фичей и таргетов.
9. `metrics_report.json` присутствует и валиден.
10. Ноутбук `notebooks/ml_report.ipynb` готов, показывает основные графики.
11. End-to-end прогон с оркестратором прошёл без ошибок на всех трёх демо-сценариях.

## Риски

1. Лабораторные анализы редкие. Часть таргетов может иметь недостаточно точек. Действие: сначала проверить количество непустых значений по каждому таргету. Если меньше 100 точек за 3.5 года - модель по этому таргету не строится, честно указывается в отчёте.
2. Задержка между АВТ и гидроочисткой. Определяется эмпирически через кросс-корреляцию признаков АВТ с серой на гидроочистке. Зашивается как параметр модели. Без этого возможна утечка будущего.
3. Экстраполяция за исторический envelope. Модели могут уверенно предсказывать для режимов, которых никогда не было. Обязательный фильтр в оптимизаторе по плотности исторических данных вокруг предлагаемой точки.
4. Дрейф данных за 3.5 года. Проверяется: MAE на позднем тесте не хуже, чем на раннем. При деградации переход на скользящее окно обучения (последние 12 месяцев).
5. Разные показатели по разным точкам отбора и фракциям. T50 фракции 240-350 и T50 фракции 350-500 - разные таргеты. Уточнение по каждой цели через справочник ЛА.
